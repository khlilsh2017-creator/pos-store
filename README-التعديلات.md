# نسخة المشروع بعد التطوير

تم تجهيز هذه النسخة لتتوافق صفحات النظام مع `worker.js` المرفق. تم تضمين `worker.js` داخل جذر المشروع حتى تكون نسخة النشر مكتملة.

## أهم ما تم إصلاحه

| المجال | التعديل |
|---|---|
| العمليات | تحديث مسارات الإرجاع والإلغاء القديمة إلى `/sales/return` و`/sales/cancel` و`/purchases/return` و`/purchases/cancel` |
| العملاء | إضافة مسارات المدفوعات الحديثة ومدفوعات اليوم ومشتريات العميل في Worker |
| الإعدادات | إضافة `/import-data` للاستعادة الآمنة المقيّدة بصلاحية المدير |
| الذكاء الاصطناعي | إضافة `/ask-gemini` كواجهة وسيطة؛ يلزم ضبط `AI_API_URL` و`AI_API_TOKEN` في متغيرات Worker |
| الطلبات | اعتماد `add_order_ph.html` كصفحة الطلب الحديثة، مع إبقاء `add_order.html` محولًا إليها للحفاظ على الروابط القديمة |
| المندوب | إصلاح جلب تفاصيل الطلب من `/orders/:id` إلى `/online-orders/:id` |
| الإشعارات | توحيد الروابط إلى `/driver/` في Worker وService Workers وصفحة اختبار الإشعارات |
| التنقل | إضافة إدارة الطلبات، تقارير الإنترنت، واجهة المندوب، حركة المخزون، واختبار الإشعارات إلى القائمة المركزية |
| التقارير | إضافة أزرار وواجهة للتقارير المحاسبية المتقدمة |
| القيود | إضافة نموذج إنشاء القيد اليدوي مع التحقق من توازن المدين والدائن |
| التنظيم | إعادة تسمية النسخ المربكة إلى `notification-test.html` و`stock-movements.html` |
| Worker | حماية مسارات الاختبار والتوكنات، وإصلاح حساب صافي الدخل داخل الميزانية |

## متغيرات البيئة الإضافية

لتمكين قسم الذكاء الاصطناعي، أضف إلى إعدادات Worker:

```text
AI_API_URL=https://your-provider.example/v1/ask
AI_API_TOKEN=your-secret-token
```

يجب أن يعيد مزود الذكاء الاصطناعي JSON يحتوي على `answer` أو أن تكون الاستجابة نفسها قابلة للعرض. إذا لم يتم ضبط هذه المتغيرات فستعرض الصفحة رسالة واضحة بدل استدعاء مسار غير موجود.

## طريقة النشر

يجب نشر ملفات الواجهة على نفس النطاق الذي يقدمه النظام، ونشر محتوى `worker.js` على Worker API، ثم التأكد من أن `API` أو `API_BASE` في الصفحات يشير إلى عنوان Worker الصحيح. بعد النشر، امسح كاش Service Worker أو ارفع رقم إصدار الكاش عند الحاجة.

## الاختبارات المنفذة

تم فحص صياغة `worker.js` وملفات Service Worker وجميع JavaScript المضمنة في صفحات HTML. كما تم فحص عدم وجود روابط المسار القديم أو مسارات العمليات القديمة أو أسماء النسخ القديمة داخل ملفات المشروع النهائية.

## قيد التأسيس الشامل وجرد المخزون

تمت إضافة `POST /accounting/initialize` بصلاحية المدير فقط لإنشاء قيد تأسيس واحد متوازن باستخدام `checkBalance` و`createJournalEntry`. بعد نجاح القيد يُفعّل المفتاح `system_initialized=1` في جدول `settings`، وتُرفض أي محاولة لاحقة لإنشاء قيد تأسيسي جديد برسالة واضحة.

تمت إضافة `POST /inventory/adjust` مع alias هو `POST /inventory/count`، وكلاهما بصلاحية المدير. يقبل المسار `adjustment_date` و`items` و`note`، ويحسب الفرق بين الكمية الحالية والكمية المرصودة، ويسجل حركة `stock_movements` بالمرجع `inventory_adjust` وينشئ قيد تسوية متوازنًا بين حساب المخزون وحساب فروقات الجرد داخل معاملة واحدة.

تم منع تحديث `stock_quantity` عبر `PUT /products/{id}`، كما أُوقف مسار `/api/update-stock` القديم برسالة توجيه إلى واجهة الجرد. وأزيل دعم `opening_balance` من إنشاء وتحديث المنتجات. أنشأت واجهات المنتجات والطلبات والمشتريات المنتج الجديد بكمية صفر عند الحاجة، وتستخدم `/inventory/adjust` عند إضافة أو استيراد كمية فعلية.

```json
{

```

```json
{
  "adjustment_date": "2026-08-23",
  "items": [
    { "product_id": 5, "new_quantity": 20 },
    { "product_id": 8, "new_quantity": 5 }
  ],
  "note": "جرد نهاية الشهر"
}
```

## توحيد الأرقام والشريط الجانبي
تم تحديث `number-utils.js` ليحوّل الأرقام العربية والهندية والفارسية إلى ASCII (`0123456789`) أثناء الكتابة واللصق وقبل الإدخال والتغيير، ويحوّل الفاصل العشري العربي إلى نقطة. يطبّق التطبيع على جميع `input` و`textarea` الرقمية، بما فيها `type="number"` و`inputmode="numeric|decimal"` و`type="tel"` والحقول الموسومة `data-numeric` أو `data-number`. تُحذف فواصل الآلاف من قيمة الحقل الرقمي حتى تبقى صالحة للمتصفح وواجهات API، بينما تُعرض القراءات بواسطة `Intl.NumberFormat('en-US')` مع فواصل الآلاف.

## سجل النشاط والتحقق من هوية المستخدم

تمت إضافة جدول `audit_logs` الذي يسجل تلقائيًا طلبات API والصفحات التي يفتحها المستخدم عبر `auth/me`. يتضمن السجل المستخدم والدور والعملية والطريقة والمسار ومعرف المورد ورمز الاستجابة والنجاح أو الفشل والتفاصيل المختصرة وعنوان IP ووقت التنفيذ، مع عدم تسجيل كلمات المرور أو محتوى كلمات المرور.

أضيفت صفحة `audit-logs.html` إلى القائمة الجانبية، وتدعم البحث باسم المستخدم أو المسار، والتصفية حسب العملية والنتيجة والتاريخ، وترقيم الصفحات، وتصدير CSV. تحتاج الصفحة إلى `audit.view`، بينما يحتاج التصدير إلى `audit.export`.

تم تعزيز `getCurrentUser` ليتحقق من وجود المستخدم فعليًا في قاعدة البيانات في كل طلب، ولذلك فإن حذف المستخدم أو تعطيله أو تغيير دوره يمنع استمرار جلسة قديمة من العمل. كما يعيد `/auth/me` بيانات المستخدم والصلاحيات الحالية من الخادم لتحديث `pos_user` في المتصفح.

عند فتح صفحة غير مصرح بها يظهر للمستخدم نموذج واضح بعنوان **لا توجد صلاحية** مع زر العودة للرئيسية، وتُخفى روابط الصفحات والأزرار والحقول غير المسموحة. أما استدعاء API غير المصرح به فيرجع `403` ويسجل محاولة المنع في سجل النشاط.


## إصلاح أخطاء بناء Wrangler

تم إصلاح أخطاء البناء التي ظهرت عند نشر Worker. كان السبب الأول هو كتابة Regex الخاص بمسار المقاسات بتهريب مزدوج، وأصبح الآن بصيغة JavaScript الصحيحة: `/^\\/products\\/(\\d+)\\/variants\\/?$/`. وكان السبب الثاني بقايا تعريف `scheduled` داخل دالة `handleRequest` بعد إضافة سجل التدقيق؛ تم فصل بنية Worker وإبقاء تعريف `scheduled` الأصلي مرة واحدة فقط داخل `export default`.

نجح الآن `node --check worker.js` و`npx wrangler deploy worker.js --dry-run`، بإجمالي رفع تجريبي يقارب 797 KiB مضغوطًا إلى 134 KiB. يجب أن يحتوي `package.json` في مشروع Worker على الاعتماد `@libsql/client` حتى يستطيع Wrangler حل الاستيراد `@libsql/client/web`:

```bash
npm install @libsql/client
npx wrangler deploy worker.js
```


## إصلاح الشريط الجانبي وفصل خيارات الدفع عن الأرصدة

بعد تسجيل الدخول مباشرة يعاد رسم الشريط الجانبي ويعاد تطبيق الصلاحيات، لذلك لا يحتاج المستخدم إلى إعادة تحميل الصفحة حتى تظهر الروابط المسموحة له. تمت أيضًا حماية لوحة التحكم من جلب أو عرض ملخص الصندوق والمحافظ عندما لا يملك المستخدم `cash.view`.

أصبحت صفحة `payments.html` تعرض خيارات القبض والصرف والسندات لمن يملك `vouchers.view` و`vouchers.create`، بينما بطاقة رصيد الصندوق وزر الإلغاء محكومان بصلاحيات منفصلة. صلاحية `cash.view` هي التي تسمح بعرض صفحة المحافظ والصندوق وسجل الرصيد، وليست مطلوبة لإنشاء سند قبض أو صرف. أضيفت صلاحية `vouchers.create` إلى الصلاحيات الافتراضية للكاشير، وأزيلت منه صلاحية `cash.view` الافتراضية حتى لا تظهر له الأرصدة والمحافظ تلقائيًا.


## عرض العملات والمحافظ بدون عرض الأرصدة

أضيفت صلاحيات مستقلة لهذا السيناريو. تمنح `currencies.view` المستخدم القدرة على رؤية العملات وأسعار الصرف، وتمنحه `wallets.view` القدرة على رؤية أسماء المحافظ واختيارها في نماذج الدفع، بينما تبقى `wallets.balance.view` هي الصلاحية الوحيدة لعرض أرصدة المحافظ. وتبقى `cash.view` مخصصة لرصيد الصندوق وسجل الصندوق.

حتى عند استدعاء API `/wallets` مباشرة، يعيد الخادم أسماء المحافظ وبياناتها التعريفية فقط ويزيل `balance` و`balances` وحقول الإجماليات للمستخدم الذي لا يملك صلاحية عرض الرصيد. كما تخفي الواجهة نماذج التحويل والإدارة وسجل حركات المحافظ حسب الصلاحيات، وتعرض عبارة **الرصيد غير معروض** بدل القيمة الرقمية.


## جلسة الكاشير وإدارة المندوبين وسجل النشاط المختصر

## آخر الفواتير في واجهة الجوال

أضيف داخل نافذة آخر الفواتير في `add_order_ph.html` حقل بحث يعمل برقم الهاتف أو اسم العميل أو رقم الطلب أو رقم الفاتورة، مع أزرار بحث ومسح وترقيم صفحات. يظهر زر `إسناد` داخل صف طلب الإنترنت غير المكتمل فقط عند امتلاك `delivery.orders.manage`، ويستدعي `/online-orders/assign-driver` ويسجل العملية في سجل النشاط.

لا يظهر زر الإسناد أو أي صلاحية مندوب في `sale.html`، لأن شاشة البيع العادي منفصلة عن إدارة طلبات الإنترنت. كما أن واجهة `add_order_ph.html` لا تحتوي على الشريط الجانبي.


## قاعدة تعديل طلبات الإنترنت

يمكن تعديل أي طلب إنترنت من نافذة آخر الفواتير في `add_order_ph.html` ما لم تكن حالته تدل على أنه تم توصيله أو فشل تسليمه. الحالات الممنوعة تشمل `تم التسليم` و`تم التوصيل` و`فشل التسليم` و`فشل` والقيم الإنجليزية المكافئة `delivered` و`failed` و`failed_delivery` و`delivery_failed`. يطبق هذا الشرط في الواجهة والخادم، وتسجل عملية التعديل المهمة في `audit_logs`.


## إصلاح سجل النشاط والتخطيط

تم إصلاح تسجيل العمليات المهمة ليكون مضمونًا قبل إرجاع الاستجابة، مع إضافة تسجيل عام لكل عمليات POST وPUT وPATCH وDELETE غير المعرفة كحدث متخصص، مع استثناء طلبات القراءة وطلبات سجل النشاط نفسه. تمت إضافة ترحيل آمن لأعمدة `audit_logs` لدعم قواعد البيانات القديمة.

لا تظهر نتائج سجل النشاط قبل اختيار المستخدم وفترة من وإلى. قائمة المستخدمين تُجلب من جدول المستخدمين نفسه حتى تظهر حتى عندما لا توجد سجلات سابقة، وتاريخ النهاية يُحسب شاملًا لليوم المحدد. كما تم وضع sidebar داخل `app-wrapper` ثابت لمنع ظهوره فوق أو تحت محتوى الصفحة.


## فصل تطبيق المندوب

تم إلغاء التوجيه التلقائي من `driver/index.html` إلى `orders.html` عند وجود جلسة POS. تطبيق المندوب يعتمد الآن على `driverToken` و`driverId` الخاصين به فقط، ويعرض واجهة الطلبات والإرجاعات والإحصائيات الخاصة بالمندوب. تبقى جلسة الكاشير `pos_token` مستقلة ولا تؤثر على فتح تطبيق المندوب.

## تطوير مركز العمليات والاستعلام عن الفواتير

تم إصلاح الاستعلام في `operations.html` وWorker ليقبل رقم الفاتورة الظاهر للمستخدم أو المعرف الداخلي، مع تفضيل المعرف الداخلي عند وجود تطابق. كما تم تصحيح تفاصيل فاتورة المشتريات التي كانت مغلفة داخل `purchase`، وربط بنود الفاتورة بالمعرف الداخلي الصحيح. أصبحت البنود تعرض اسم المنتج والكود والمعرف والكمية والمرتجع والمتاح للإرجاع وسعر الوحدة والإجمالي.

أضيفت من نافذة الفاتورة إجراءات التعديل والإلغاء والإرجاع الجزئي للصنف والإرجاع الكامل لفواتير المبيعات، وإرجاع صنف وإلغاء لفواتير المشتريات، مع إظهار الإجراءات حسب حالة الفاتورة وصلاحيات المستخدم. يبقى التحقق النهائي على Worker، ولا يظهر تعديل فاتورة البيع إلا للفواتير المكتملة التي يسمح الخادم بتعديلها.

## ضبط البحث عن أرقام الفواتير واختيار فواتير الإرجاع

تم فصل رقم الفاتورة الظاهر عن معرف قاعدة البيانات في مركز العمليات. يقبل البحث الآن رقمًا ظاهرًا يبدأ من 1000، مثل `1000` أو `INV-1000` أو `PUR-1000`، ويرفض الأرقام الأقل من 1000 حتى لا يتم تفسير المعرفات الداخلية مثل 1 و2 على أنها أرقام فواتير.

أضيف المسار `/operations/product-invoices` لعرض آخر فواتير البيع أو الشراء المرتبطة بمنتج محدد. تعرض قائمة مبيعات المنتج رقم الفاتورة واسم العميل والكمية والمتاح للإرجاع، بينما تعرض قائمة المشتريات رقم الفاتورة واسم المورد والكمية والمتاح للإرجاع. بعد اختيار الفاتورة تُجلب معاينتها وتُستخدم هويتها الداخلية لتنفيذ الإرجاع بأمان.

أصبحت قوائم إلغاء البيع والشراء تُملأ بالفاتورة التي تمت معاينتها، فتظهر للمستخدم رقم الفاتورة والطرف والحالة قبل تنفيذ الإلغاء، مع بقاء التحقق من الحالة والصلاحيات داخل Worker.

## إصلاح اتساق مخزون الموردين مع المخزون العام

تمت إضافة `updateSupplierStock(tx, productId, supplierId, delta, batchQueries)` لتوحيد تحديث `product_supplier_stock` داخل نفس معاملة Turso، بحيث تكون الزيادة موجبة عند استرجاع المنتج أو إلغاء العملية، والنقصان سالبًا عند البيع أو الإرجاع للمورد أو إعادة خصم عملية ملغاة. تستخدم الدالة `ON CONFLICT` وتحمي الكمية من النزول تحت الصفر، ولا تنفذ استعلامًا منفصلًا خارج الدفعة.

في `createPurchase` أصبح مقدار الإضافة إلى مخزون المورد محسوبًا بالصيغة `Math.max(0, quantity + Math.min(0, currentStock))`، مع تحديث خريطة المخزون أثناء تكرار بنود الفاتورة. بذلك يعوض الشراء العجز السابق في `products.stock_quantity` ولا يضاعف كمية الموردين.

تم توحيد التحديثات في إلغاء فاتورة المبيعات، إرجاع صنف مبيعات، الإرجاع الكامل، عكس إرجاع الصنف، عكس إلغاء الفاتورة، تعديل البيع، إلغاء الطلب الإلكتروني، فشل التوصيل، إضافة إلى إلغاء وإرجاع المشتريات. عند توفر `supplier_id` في `sale_items` يُستخدم أولًا، ثم يُستخدم أفضل مورد من `bestSupplierMap` عند الحاجة. تُنفذ تغييرات `products` و`product_supplier_stock` وسجل الحركة ضمن نفس المعاملة وبدفعات مقسمة عند المسارات التي قد تحتوي عددًا كبيرًا من البنود.

## إصلاح فتح الفواتير وإلغاء تقييد الرقم 1000

تم إلغاء التحقق الذي كان يمنع البحث عن أرقام الفواتير الأقل من 1000. أصبح مركز العمليات يقبل رقم الفاتورة الظاهر أو المعرّف الداخلي بأي قيمة رقمية، مع دعم صيغ `INV-رقم` للمبيعات و`PUR-رقم` للمشتريات.

تم إصلاح `getSaleDetails` و`getPurchaseDetails` بحيث يبحثان بالرقم الظاهر أو بالمعرف الداخلي، وأصبحت قواعد التوجيه والصلاحيات تقبل صيغ أرقام الفواتير الظاهرة. هذا يعالج فشل فتح الفاتورة من `invoices.html` وفشل تحميل فاتورة قديمة من شاشة `sale.html?edit=...`، بما في ذلك حالة الاستعلام عن `/sales/685`.

## إصلاح إرجاع المشتريات والكمية الفعلية المتاحة

تم إصلاح خطأ `batchQueries is not defined` في `returnPurchaseItem`. أصبحت العملية تنشئ `batchQueries` قبل إضافة سجل الإرجاع وتحديث المنتج ومخزون المورد، ثم تنفذها داخل نفس المعاملة قبل `commit`.

قبل تنفيذ إرجاع مشتريات، يحسب Worker الكمية المتاحة فعليًا باعتبار الأقل من الكمية المتبقية في بند فاتورة الشراء، والمخزون العام للمنتج، ومخزون المورد عند وجود سجل له. إذا لم توجد كمية كافية، تُرفض العملية برسالة توضح المخزون العام ومخزون المورد والكمية المتاحة بدل تنفيذ إرجاع غير صحيح.

كما أصبحت تفاصيل فاتورة الشراء وتاريخ فواتير المنتج يعرضان `actual_stock_quantity` و`supplier_stock_quantity` و`returnable_quantity`، وتعرض شاشة العمليات هذه القيم وتعبئ كمية الإرجاع تلقائيًا بالحد الفعلي المتاح.

## إصلاح العملات والمحافظ ومبالغ الدفع في تطبيق المندوب

تمت إضافة `currencies.view` و`wallets.view` إلى الصلاحيات الافتراضية للـ driver حتى يستطيع تطبيق المندوب تحميل العملات وأسماء المحافظ من خلال جلسة `driverToken` المستقلة. لم تُضف صلاحيات `wallets.balance.view` أو `cash.view`، لذلك تبقى أرصدة المحافظ مخفية.

تمت إضافة `parseDriverAmount` المعتمد على `POSNumberUtils.toNumber`، وهو يحول الفواصل العربية والإنجليزية والأرقام العربية والفارسية قبل الحساب. كما تم إصلاح قراءة المبلغ المستحق من النص المنسق؛ فأصبح `5,900` أو `٥٬٩٠٠` يُقرأ كـ `5900` بدل `5` أو `5.0`. ويُستخدم نفس التحويل في مبالغ النقد والمحفظة وأسعار الصرف.

## توحيد توقيت اليمن في الإنشاء والعرض

تم اعتماد المنطقة الزمنية `Asia/Aden`، وهي توقيت اليمن UTC+03:00. يبقى التخزين في SQLite بصيغة UTC القياسية عند استخدام `CURRENT_TIMESTAMP`، بينما تُحوّل السجلات عند العرض والتصفية إلى توقيت اليمن.

تم تطوير `date-utils.js` بدوال `inputToUTC` و`toLocalInput` و`localized`. عند إنشاء أو تعديل طلب من حقل `datetime-local` تُفسر القيمة كتوقيت اليمن ثم تُحفظ UTC، وعند فتح الطلب تُعاد إلى حقل الإدخال بتوقيت اليمن. كما تم توحيد عرض الأوقات في تطبيق المندوب، الفواتير، الطلبات، المشتريات، سجل النشاط، الصندوق، المحافظ، السندات، المصروفات، وكشوف العملاء.

## السماح للعملات والمحافظ للمندوب ورسوم التوصيل عند الاستلام

تم تعديل بوابة الصلاحيات في Worker بحيث يسمح `GET /currencies` بصلاحية `currencies.view` فقط، ويسمح `GET /wallets` بصلاحية `wallets.view` فقط. كما تُضاف هذه الصلاحيات تلقائيًا لكل حساب بدور `driver` حتى لو كانت له صلاحيات مخصصة قديمة. لم تُمنح صلاحيات `wallets.balance.view` أو `cash.view`، لذلك لا تظهر أرصدة المحافظ أو بيانات الصندوق.

تم توحيد حساب المبلغ المستحق. الطلب المدفوع مسبقًا لا يطلب قيمة المنتجات من المندوب، لكن إذا كانت `delivery_fee_payment` مساوية لـ «عند الاستلام»، يعرض النظام رسوم التوصيل فقط كمبلغ مستحق، ويسمح بتسجيل تحصيلها عند تأكيد التسليم. أما `total_amount` فيبقى دون إضافة رسوم التوصيل مرة ثانية لأنه يتضمنها أصلًا.

## تطوير عرض الفواتير وخصم البنود

تم توحيد قالب الفاتورة في `document-utils.js` بحيث يكون رأس الفاتورة مختصرًا ومنظمًا، وتظهر هوية المنشأة ورقم المستند والتاريخ وبيانات العميل أو المورد بطريقة متجاوبة. يميز القالب بين البيع العادي وفاتورة الشراء وفاتورة طلب الإنترنت، ويعرض لطلب الإنترنت رقم الطلب والهاتف والعنوان والمحافظة ونوع التوصيل والمندوب.

تظهر ملاحظات الطلب وملاحظات كل منتج داخل الفاتورة، ويظهر خصم كل منتج كسعر خصم للوحدة وإجمالي الخصم للبند، مع فصل خصم المنتجات عن خصم الإجمالي في قسم المجاميع.

تمت إضافة حفظ خصم المنتج وملاحظته في `sale_items`، وترحيل عمود `note`، وتطبيق الخصم على الحساب في `createSale` و`updateSale`. كما تمت إضافة حقول الخصم والملاحظة إلى شاشة البيع وتعبئة هذه البيانات عند فتح فاتورة قديمة للتعديل، وتحديث عرض الفاتورة في `invoices.html` و`orders.html` و`operations.html` و`online-reports.html` و`customers.html` وتطبيق المندوب.

أضيف `phone/sw_phone.js` كعامل Service Worker خفيف لتخزين ملفات واجهة الهاتف فقط وتسريع التنقل، مع عدم تخزين استجابات API أو البيانات الحساسة. كما أضيف مؤشر تحميل مركزي بدائرة متحركة يظهر أثناء جلب القوائم والتفاصيل والتسوية والإرجاعات والطباعة.

## إصلاح أزرار التسوية وكشف الحساب وآلية استلام طلبات المندوب

تم إصلاح خطأ JavaScript في `phone/orders.html` الذي كان ينتج `Unexpected end of input` عند الضغط على تسوية أو كشف الحساب. كان السبب تمرير اسم المندوب داخل `onclick` بعلامات اقتباس غير آمنة؛ أصبح التمرير الآن محميًا، وتعمل أزرار التسوية وكشف الحركة حتى مع أسماء تحتوي على اقتباسات.

أضيف جدول `driver_order_receipts` لتسجيل استلام الطلب من المندوب دون تغيير حالة الطلب الأصلية. الطلبات التي حالتها غير مكتملة أو فشل توصيلها تظهر ضمن الطلبات المتبقية حتى يسجل المدير استلامها. الطلبات المسلّمة أو الملغاة أو المرتجعة لا تظهر ضمن قائمة الاستلام.

أضيفت للمسارين `/drivers/unreceived-orders` و`/drivers/receive-orders` صلاحيات عرض وإدارة المندوبين. تعرض واجهة الكمبيوتر والجوال لكل مندوب عدد الطلبات غير المستلمة وقيمتها الإجمالية وعدد الطلبات الفاشلة.

عند فتح **تسوية استلام الطلبات** تظهر نافذة تحتوي على اسم المندوب وعدد الطلبات المتبقية والقيمة الإجمالية وعدد الطلبات الفاشلة، ثم قائمة بكل طلب مع رقم الطلب والعميل والحالة والسعر. يمكن تنفيذ **تم استلام الطلب** لكل طلب منفردًا أو الضغط على **تم استلام الكل**. كل عملية تسجل صفًا في `driver_transactions` من النوع `order_receipt` بقيمة صفرية حتى تظهر في كشف الحركة دون تغيير الرصيد المالي، وتسجل أيضًا في `audit_logs`.

تبقى التسوية المالية منفصلة عن تسوية استلام الطلبات: التسوية المالية تسجل النقد أو المحفظة وتغير رصيد المندوب، بينما استلام الطلبات يثبت أن الطلبات المتبقية أو الفاشلة عادت إلى المحل ويحدث عدد الطلبات الظاهر للمندوب.

## إصلاح نافذة تسوية المندوب وتحديد فترة كشف الحساب

تم تصحيح نافذة التسوية المالية في `phone/orders.html` بحيث لا تظهر حقول مبالغ مكررة. في طريقة النقد أو المحفظة يظهر حقل المبلغ الإجمالي مرة واحدة فقط، وتظهر حقول النقد والمحفظة التفصيلية فقط عند اختيار طريقة الدفع المختلطة.

تم فصل فتح كشف الحساب عن تحميل البيانات. عند الضغط على زر **كشف الحركة** تظهر لوحة التصفية الموحدة مباشرة، ويطلب التطبيق تحديد تاريخ البداية والنهاية ثم الضغط على تطبيق. بعد التطبيق تُحفظ الفترة ويُحمّل الكشف للمندوب المحدد، وتُستخدم الفترة المحفوظة نفسها عند الطباعة.
